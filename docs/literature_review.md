# Literature review: LLM-based bug/fault localization (2024-2026)

Scope: papers on using LLMs (with or without retrieval) to predict which source file(s)/function(s) need to change to fix a bug, given a bug report/issue. Grounds the four things asked for in the project brief: compare algorithms/datasets/metrics, unify benchmark handling, design offline code representation + vector indexing, and evaluate hybrid retrieval/reranking/AST/semantic-similarity methods for Top-1 accuracy.

**Baselines named in the original handover doc:** BLAZE, BugCerberus, FlexFL, MarsCode. Status: BLAZE, BugCerberus, and FlexFL have been located below. **MarsCode has not yet been found** in either research pass — needs a targeted follow-up search.

## Priority tiers

### Tier 1 — core (must include)

| Paper | Why it matters |
|---|---|
| BugCerberus — *Bridging Bug Localization and Issue Fixing: A Hierarchical Localization Framework Leveraging LLMs* | Directly studies hierarchical retrieval (file → function → statement) on SWE-bench Lite; measures Top-k localization and repair improvement. Named in the original handover doc. |
| BLAZE — *Cross-Language and Cross-Project Bug Localization* | Introduces dynamic chunking, the BeetleBox benchmark, evaluates on SWE-bench with Top-1/MAP/MRR. Directly relevant to chunking design. Named in the original handover doc. |
| Kept — *A Knowledge Enhanced Large Language Model for Bug Localization* | Uses knowledge graphs to enhance LLM retrieval; compares against GraphCodeBERT, CodeT5, OpenAI embeddings. |
| Toggle — *A Deep Dive into Large Language Models for Automated Bug Localization and Repair* | Strong baseline paper; token-level vs. line-level localization and prompt engineering. |

## Key trends across all research passes

1. **No retrieval is (mostly) the losing strategy, but the margin varies a lot.** Every paper using a real retrieval/agent step outperforms pure-prompting baselines, but the size of the gap ranges from modest (BLAZE's 29% vs. this project's 43-52%) to enormous (LocAgent/Meta-RAG's 77-85% vs. this project's ~50%). The two very top performers (LocAgent, Meta-RAG) don't use vector embeddings at all — see trend 4.
2. **Hierarchical retrieval (file → function → statement/class) is the dominant pattern** among the strongest systems (BugCerberus, LocAgent, KGCompass, Kept), not flat file-level or symbol-level alone.
3. **Dynamic/semantic chunking beats fixed-size or whole-file chunking, confirmed by two independent papers.** BLAZE segments at class/method/interface AST boundaries; the Cross-language PLM paper directly shows whole-file embedding (3-12% Acc@10) is dramatically worse than 512-token chunked embedding (33-71% Acc@10) — over 400% relative improvement from chunking alone, independent of any other architecture choice.
4. **Sparse/lexical retrieval (BM25) repeatedly beats or matches dense embeddings, and is far simpler to build.** LocAgent's own ablation shows BM25 indexing is its single most critical component (bigger than the graph structure itself); ExpeRepair explicitly tested embeddings vs. BM25 for memory retrieval and BM25 won; SWE-Fixer, IQLoc, and LinuxFL+ all rely on BM25 with no vector DB at all. **A vector database may not be necessary at all for a first serious iteration of this project** — a BM25-based coarse filter is cheaper to build, has no embedding-model choice to make, and is backed by more of the strongest results in this review than dense retrieval is.
5. **"Compress the codebase into summaries" is a highly competitive, low-infrastructure alternative to retrieval.** Meta-RAG achieves 84.67% file-level accuracy purely by having an LLM generate hierarchical natural-language summaries once (no vector DB, no fine-tuning, no BM25) and reasoning over those instead of raw code — the single cheapest-to-replicate idea in this entire review, and directly applicable to this project's existing whole-file-list prompt (replace bare paths with one-line summaries).
6. **More context in a prompt is non-monotonic — it can actively hurt, and two independent papers confirm the mitigation.** MANIPLE (Fact Selection) shows pass@1 degrades past a context threshold; SWE-Fixer's own ablation shows adding full file content (vs. compact skeletons) *drops* retrieval precision/recall; Hierarchical Knowledge Injection shows dumping all context layers at once underperforms adding them incrementally. This directly implicates this project's current design (entire file-path list, unfiltered, in one prompt) as a likely source of the accuracy ceiling, independent of any retrieval architecture decision.
7. **Bug-report text alone is a weaker signal than most of the strongest FL literature assumes.** AutoFL, FlexFL, MemFL, and DEVLoRe all rely on dynamic signal — failing test execution, stack traces, or debugging info — not just the issue description text this project currently uses exclusively. DEVLoRe's own numbers show issue+stack-trace beats issue-alone by ~6 points; this is a cheap addition to test since SWE-bench's patch/traceback data may already contain this signal without needing any new retrieval infrastructure.
8. **Project/repository-level memory of past repairs is the biggest lever for pure Pass@1 (repair) results** (ExpeRepair 74.6%), but its own authors admit localization itself is under-optimized in that design — a reminder that a system can produce a great headline repair number while still solving localization worse than this project's more focused scope.
9. **Localization and repair are increasingly treated as separable stages** (Toggle, "How Far Are We?" survey) — and the survey paper directly confirms accurate file-level localization correlates strongly with final fix success, validating this project's decision to focus on localization alone rather than also attempting patch generation.
10. **Findings don't transfer across codebase scale.** LinuxFLBench shows the same agent (SWE-Agent) drops ~17 points of Recall@1 going from SWE-bench-lite-sized repos to the Linux kernel — a caution against assuming any of these numbers (including this project's own, on repos like Django/matplotlib) would hold on a much larger codebase.
11. **Issue-description quality is a bigger predictor of solvability than architecture choice.** The "How Far Are We?" survey found this to be the single strongest factor distinguishing cases every system solves from cases none can — a confound to keep in mind when comparing Top-1 numbers across different benchmark subsets/sampling.
12. **Metric mismatch risk remains important:** several top numbers (ExpeRepair, SWE-Fixer, DEVLoRe's fix rate, Hierarchical Knowledge Injection) report Pass@1 or Fix Rate — requiring a working generated *patch*, not just correct file identification. This project's `evaluate.py` measures pure localization Top-1 (hit@k on file paths only) — the "Quick reference" table above only includes numbers on the same metric family to stay a fair comparison.
