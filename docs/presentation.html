Phase 4 — Pipeline

The pipeline in one line

Two stages that run offline (candidates for MN5), one that needs a live LLM call (never can).

Input
Bug report text
→
Stage 1 · offline
BM25 over symbol-enriched docs — narrows repo to top‑200 candidates
→
Stage 2 · offline
Chunked embedding rerank, fused with BM25 via weighted RRF
→
Stage 3 · needs internet
gpt‑4o‑mini reranks the shortlist → Top‑1 file

This split is why MN5 (no outbound internet by design) can only ever host Stages 1–2 — not a limitation to work around, a structural boundary that scopes what MN5 execution means for this project.

Phase 2 — Generalization

Bench4BL: a real content-fetching bug found and fixed, then a real Java result

Bench4BL (ISSTA 2018, 100% Java) looked tied across every BM25 representation at first — not a language-parsing limit as first assumed, but a real bug: BM25/embedding retrieval was never reading Bench4BL's file content at all, silently falling back to path-only tokens for every instance. Fixed, plus a new Java-aware lexical scanner added on top.

BM25 representation, n=30 (corrected)
0.1.2.3.4+
path_only
0.272
symbols_no_imports
0.317
symbols_with_imports
0.366
skeleton
0.413

All four representations now genuinely differ (they used to tie exactly) — real signal, not the old fetch-bug artifact.

Root cause

bm25_retriever.py / embedding_retriever.py fetch content via repo_cache.py's is_repo_cached(), which only checked repo_cache/ — SWE-bench/BeetleBox's mirror directory. Bench4BL's content lives in bench4bl_cache/<PROJECT>/gitrepo instead, so the check was always False and every representation silently degraded to path tokens.

Fixed with a Bench4BL fallback path in repo_cache.py (same git cat-file --batch mechanism). A prior write-up had blamed this on Python-only AST parsing — that explanation was wrong, or at least incomplete; this was the real cause. A second, bigger catch: the original n=30 hybrid RRF result (0.5424 MRR) was built on the same broken plumbing and is void too — see next slide.

Phase 6 — MN5 execution

MN5: four blockers resolved, dozens of real Slurm jobs since

Account comm842299 / project ehpc680, acc (GPU) partition. Four blockers found while getting the real retrieval stack running on the cluster — all four now resolved live.

1
huggingface-hub version conflict resolved
Wheelhouse had an incompatible version with no PyPI fallback (offline cluster) — fixed by shipping the correct wheel over scp.
2
torch missing from the venv resolved
Never installed on the cluster venv at all — installed torch==2.6.0+cpu plus a matching tokenizers pin from the wheelhouse.
3
MN5's checkout predated the embedding/hybrid work resolved
Missing files pulled from the correct branch and transferred via scp — not a git clone, so future gaps still surface one ModuleNotFoundError at a time.
4
No outbound internet blocks HuggingFace model downloads resolved
Pre-downloaded Qwen3-Embedding-0.6B weights locally (1.8GB), transferred the HF cache directory via scp, set HF_HUB_OFFLINE=1 — confirmed loading fully offline on MN5. A same-shape follow-on bug surfaced immediately after: HF_HUB_OFFLINE=1 also silently blocked datasets.load_dataset() from fetching SWE-bench Verified itself, not just model weights — fixed by pointing SWEBENCH_LOCAL_PATH at the already-mirrored local copy.

Also required mirroring 4 repos MN5 didn't have (flask, requests, sphinx, seaborn — the full 12-repo SWE-bench Verified set, discovered because the sweep script scans the entire 500-instance pool before filtering to the 30 wanted, not just those 30's own repos) and generating a dedicated SSH key, since no access to MN5 existed from this machine at all going in. Open, not blocking correctness: MN5 has torch==2.6.0+cpu installed, so --gres=gpu:1 allocations sit unused — every job so far, including today's, runs at CPU speed. This is why array-job sharding (splitting long runs across parallel Slurm tasks instead of one long serial job) has become the standard pattern for anything slow, rather than fixing the underlying GPU issue directly.
